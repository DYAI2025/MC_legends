### B2 — Failure visibility: status file, notification, freshness check

- **REQ:** MCL-65-AC6
- **Files:** `scripts/backup-mc-legends.sh` (wrapper hooks), new
  `scripts/check-backup-freshness.sh`, new test
  `tests/unit/check-backup-freshness.test.ts` (with the required prose header naming the
  failure it pins), possibly `scripts/check-foundation.mjs` (append new load-bearing
  files to the required-paths list)
- **Design (small, honest):**
  - Every run appends one line `<stamp> ok|FAILED <exit>` to `~/Backups/mc-legends/runs.log`
    and rewrites `~/Backups/mc-legends/last-run.status` — written from an EXIT trap so a
    failed run *records* its failure instead of leaving silence (AC6: a failed run must
    never look green; today it only looks *absent*).
  - On non-zero exit the wrapper posts a macOS notification (`osascript -e 'display
    notification …'`) — operator-visible without opening a log.
  - `scripts/check-backup-freshness.sh <dir> [max-age-hours=48]`: exit 1 + stderr message
    when the newest **verified** set is older than the ceiling or `last-run.status` says
    FAILED; exit 0 otherwise. This catches the silent-absence case (Mac asleep for days,
    ssh key broken) that per-run notification cannot.
  - No network, no secrets in any of it; freshness script is pure-local so the unit test
    can run it in CI (same pattern as `verify-media-archive.sh`).
- **Tests to run:** `npm run verify` (shellcheck in CI covers the shell); new unit test
  proves: fresh set → 0, stale set → 1, FAILED status → 1, empty dir → 1 (refuse-on-empty
  convention).
- **Acceptance evidence:** unit test green; a deliberately-broken manual run (e.g.
  `MCL_BACKUP_VPS=root@invalid.invalid`) exits non-zero, writes `FAILED` status, fires
  the notification; freshness script then exits 1.

## Risks and rollback notes

| Risk | Mitigation / rollback |
|---|---|
| MacBook asleep/away for days → no backup runs | launchd runs missed calendar jobs on wake; `check-backup-freshness.sh` makes the gap visible instead of silent; documented honestly as the MVP's cadence limit (G2). Moving to an always-on second host is a future ticket, not smuggled in now. |
| Backup pull runs while a child is uploading | Set is still internally consistent: dump is transactional, media manifest is source-side; worst case the newest recording appears in the next run. No mitigation needed beyond the correlation stamp. |
| Deliberate failure test (B2) leaves a FAILED status that scares a later reader | The next real run overwrites `last-run.status`; runs.log keeps history — that is the point. |
| Restore drill touches the wrong DB | Drill DB name carries the stamp, port 5433 local, commands never mention the VPS `mcl`; runbook already forbids restoring over `mcl`. |
| `launchctl bootstrap` fails (already-loaded label from an old experiment) | `launchctl bootout gui/$(id -u)/com.dyai.mcl-backup` first, then bootstrap; plist is idempotent to reinstall. Uninstall = bootout + delete plist — full rollback of B4 with zero data impact. |
| Jira transition premature (a V1 check fails after closure) | Transitions are reversible; but the plan's ordering (V1 gates everything, C5 last) exists to make this a non-event. |
| Runbook edits delete historical evidence | C1/B6 follow the keep/move/drop rule: superseded sections are marked historical, measurement rows are never dropped. |
| `check:foundation` breaks on new files | B2/B3 append new load-bearing paths to the required list in the same commit that adds them. |
