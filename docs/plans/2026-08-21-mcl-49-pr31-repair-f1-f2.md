## 1. Goal

Close two review findings on PR #31 without changing any behaviour the review already
accepted:

- **F1** — make 8 MiB (`8388608` bytes) a **structural upper bound** on accepted audio, so
  no environment value can widen the upload route past what migration `0002` allows. Today
  `audioMaxBytes()` returns any positive `AVALORIA_AUDIO_MAX_BYTES`, which in PostgreSQL
  mode buys an orphan blob written before the `CHECK` refuses the row, and in
  `FileSubmissionInboxStore` rollback mode buys a stored, acknowledged, oversized recording
  with no constraint anywhere to stop it.
- **F2** — make a *successful* media backup prove the **transferred bytes**, not just that
  the tar lists and the file count matches, and stop a missing media directory from silently
  producing a green DB-only backup once audio persistence is live.

## 4. Reading of the F1 evidence list — one ambiguity, resolved explicitly

The finding asks for "8 MiB body is refused before blob persistence" **and** for "ENV
exactly 8 MiB → accepted". Taken literally those contradict each other, and they also
contradict P8, which PR #31 already pins with a passing test and a deliberate comment
("The cap is `>`, not `>=`: a body of exactly maxBodyBytes is the documented maximum and
has to be accepted").

**Resolution used by this plan:** the refusal cases are read as *a body above the effective
maximum* — concretely `8388609` bytes — in the scenario where `AVALORIA_AUDIO_MAX_BYTES`
has been set **above** 8 MiB. That is the actual defect F1 describes (a widened route), and
it is what T4 tests, in both store modes. A body of exactly `8388608` stays accepted.

If the reviewer meant the literal reading, that is a product change (lowering the maximum
below the documented one) and belongs to a different ticket, not to a bounded repair.

## 5. F1 — design

### 5.1 Decisions

**D-F1-1 — the ceiling is a domain constant, not a composition-root constant.**
`MAX_AUDIO_BYTES = 8 * 1024 * 1024` moves into `src/domain/media/audio-artifact.ts`,
alongside `AUDIO_MIME_EXTENSIONS`. Reasons: it is a product invariant of the same class as
the allowlist; the domain is the one layer both the route, the adapters and the composition
root may import (dependency direction stays downward); and putting it there is what lets the
route, the file adapter and the composition root agree *structurally* instead of by three
copies of a number. `src/composition/server.ts` keeps the environment read — it stays the
only module in `src` that touches `process.env`.

**D-F1-2 — clamp, do not refuse: `effectiveMax = min(configured, MAX_AUDIO_BYTES)`.**
An over-wide value is a configuration typo, not a missing credential. The gates'
`unavailable` path exists because a missing secret must close the door; taking the upload
route down over a size typo would turn a harmless mistake into an outage for a child. The
clamp fails safe in the only direction that matters: the door can never open wider than the
product decided. Lowering still works, unchanged.

**D-F1-3 — the clamp is loud.** `audioMaxBytes()` emits one `console.warn` per process with
a fixed log string when the configured value exceeds the ceiling, guarded by a module-level
flag in the same style as the lazily-created rate limiters. A silently ignored configuration
value is the failure mode this repo's own principle forbids ("what doesn't work should fail
visibly"). The string names no secret and no child text.

**D-F1-4 — `describeAudioArtifact` refuses a size above the ceiling.** This is the
structural backstop that covers callers that do not go through the composition root. It is
already invoked *before* the blob write in the route, so it cannot leave an orphan blob. It
throws rather than returning a sentinel, matching `audioObjectKey`'s existing policy: a
caller that gets here with an oversized size skipped a guard, and that is a bug, not an
attack to be quietly absorbed. With D-F1-2 in place it is unreachable from the route — which
is the point of a backstop.

**D-F1-5 — the file store gains the file-mode equivalent of the DB `CHECK`.**
`FileSubmissionInboxStore.appendIfAbsent` throws `SubmissionPayloadError` for an audio
record whose `audio.sizeBytes` exceeds the ceiling. `PostgresSubmissionInboxStore` already
produces exactly that error for `23514` (check violation), so this makes the two adapters
answer the same way, and the shared contract suite becomes the proof for both. This is the
direct answer to F1's second bullet, and it does **not** make the app depend on the `CHECK`
to repair anything — the route's clamp is the application-level fix; these are the floor
under it.

**D-F1-6 — `readInboxRecord` / `readAudioArtifact` are deliberately NOT changed.**
`src/adapters/persistence/inbox-record-shape.ts` is a **read** path whose documented policy
is to skip an unreadable line rather than refuse it, and it explicitly declines to mirror
schema caps so it can never reject a line it wrote itself. With D-F1-5 in place no line above
the ceiling can be written, so mirroring the cap on the read side buys nothing and risks the
exact failure that comment warns about. Recorded as a conscious non-change.

### 5.2 Shape of the edits

```ts
// src/domain/media/audio-artifact.ts
/**
 * The largest recording this project stores, in bytes. 8 MiB, decided 2026-08-21.
 * A product decision, which is why it lives here and not next to the environment read:
 * the upload route, the inbox adapters and the composition root all have to agree on it,
 * and this module is the one place all three may import.
 * Widening it is a schema migration (submission_inbox_media_size_bounded in 0002), never
 * a configuration change.
 */
export const MAX_AUDIO_BYTES = 8 * 1024 * 1024;
```

```ts
// src/composition/server.ts
export function audioMaxBytes(): number {
  const configured = positiveInteger(process.env.AVALORIA_AUDIO_MAX_BYTES, MAX_AUDIO_BYTES);
  if (configured > MAX_AUDIO_BYTES && !warnedAboutAudioMaxBytes) {
    warnedAboutAudioMaxBytes = true;
    console.warn("AVALORIA_AUDIO_MAX_BYTES exceeds the product maximum and was clamped");
  }
  return Math.min(configured, MAX_AUDIO_BYTES);
}
```

`DEFAULT_AUDIO_MAX_BYTES` is deleted; `MAX_AUDIO_BYTES` is imported from the domain and used
as both the default and the ceiling, so the two can never drift apart.

## 6. F2 — design

### 6.1 Decisions

**D-F2-1 — verification is its own committed script, not more lines in the backup script.**
`scripts/verify-media-archive.sh <tar> <manifest>` is a pure predicate: extract, check,
clean up, exit 0 or non-zero. Splitting it out is what makes it **testable without SSH,
without PostgreSQL and without a VPS** — the backup script cannot be exercised end to end in
CI because it shells to `ssh`, `pg_dump` and `pg_restore`. The caller keeps the policy
(quarantine as `.corrupt`, fail the run, do not prune); the verifier keeps the proof.

**D-F2-2 — the proof is the source-side manifest, re-checked against extracted bytes.**
`sha256sum -c` where available, `shasum -a 256 -c` otherwise — the VPS writes the manifest
with `sha256sum`, the backup runs on macOS, and both tools read that same
`<digest>␠␠<path>` format. The digest check proves *manifest ⊆ archive*; a second check —
extracted regular-file count equals manifest line count — closes the other direction, so an
archive carrying a file nobody vouched for also fails.

**D-F2-3 — extraction is into `mktemp -d`, removed by an `EXIT` trap.** Never into `$SET`,
never near `/opt/mc-legends/data/media`, never with `tar -P`. Production files are read and
nothing else. A failed verification still cleans up the temp tree; what it preserves is the
downloaded archive, renamed `.corrupt`, exactly as the dump path already does.

**D-F2-4 — pruning and `ok:` move behind the verification.** `find … -mtime +$KEEP_DAYS
-exec rm -rf` and every `echo "ok: …"` line already sit after the media block; the new check
is inserted *inside* that block, before them, and `fail` exits non-zero — so a suspect set
cannot cause an old good set to be deleted, and cannot print success.

**D-F2-5 — `MCL_BACKUP_REQUIRE_MEDIA=1` turns an absent media directory into a hard
failure.** Unset, or any value other than the literal `1`, keeps today's behaviour exactly
(a warning on stderr, `media: none` in the summary, exit 0) — which is what pre-audio
production needs and what the 2026-08-21 drill row records. A *present but empty* directory
is **not** a failure under the flag: that is the legitimate state between enabling audio and
the first upload, and conflating the two would recreate the ambiguity the existing script
went out of its way to separate.

**When the flag becomes mandatory** — stated as a check, not a feeling:

```bash
# On the VPS. Both true ⇒ MCL_BACKUP_REQUIRE_MEDIA=1 is required from that moment on.
grep -q '^AVALORIA_MEDIA_DIR=' /opt/mc-legends/app.env
docker exec mc-legends psql "$DATABASE_URL" -Atc \
  "select count(*) from submission_inbox where kind='audio'"   # > 0
```

From the first audio row onward, a missing media directory is data loss rather than a
pre-audio state, and a green DB-only backup is a lie. The flag belongs in the launchd job's
environment at that point.

**Considered and rejected:** a `MEDIA-VERIFICATION-FAILED` marker file in the set directory.
`.corrupt` is already this script's quarantine convention and a second one would have to be
learned; `fail` writes to stderr, which launchd captures.

### 6.2 Shape of the caller change

```bash
REQUIRE_MEDIA="${MCL_BACKUP_REQUIRE_MEDIA:-0}"
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
...
if [ "$MEDIA_STATE" = "absent" ]; then
  if [ "$REQUIRE_MEDIA" = "1" ]; then
    fail "$VPS:$MEDIA_DIR does not exist and MCL_BACKUP_REQUIRE_MEDIA=1"
  fi
  ... existing warning, unchanged ...
else
  ... existing manifest, tar and count check, unchanged ...

  # THE PROOF: the transferred bytes, against the manifest taken at the source.
  if ! "$SCRIPT_DIR/verify-media-archive.sh" "$MEDIA_TAR" "$MEDIA_MANIFEST"; then
    mv "$MEDIA_TAR" "$MEDIA_TAR.corrupt"
    fail "media archive does not match the source manifest - quarantined as $MEDIA_TAR.corrupt"
  fi
fi
```
